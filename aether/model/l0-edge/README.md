# asolaria-l0-edge

Integer-only Rust port of the trained Asolaria L0 EdgeLevelGNN: from graph-runtime events, through
the feature extractor the model was trained on, to the edge score the L0 server on port 4792
returns. Crate `asolaria-l0-edge`, library `l0_edge`, no dependencies, `#![forbid(unsafe_code)]`,
Rust 1.81, no `f32`/`f64`.

**Lane.** Everything under `src/` is hot lane: it runs per request, in process, on integers and
HBP text, with no Python, torch, Node, JSON or HTTP. `tools/` and the vendored upstream files are
cold lane: they exist to verify the port in CI and never run per request. Every tool here computes
in integers only (JavaScript numbers held as binary64 bit patterns, exact rationals as integer
pairs, float32 values read by their bit patterns). Float runs only in the owner's own code that
`tools/model_parity.py` runs unchanged: torch with the trained float32 checkpoint, and numpy in the
vendored `build_node_features`. Provenance, the vendor table and the measured agreement are in
[`PROVENANCE.md`](PROVENANCE.md).

## Modules

| Module | Port of | Public API |
|---|---|---|
| `event` | the event fields `extractNodeFeatures` reads (gnnDataExport.js:29-49) | `Event`, `parse_events`, `EventError`, `MAX_RISK_SCORE`, `MAX_EVENTS` |
| `features` | `extractNodeFeatures` (gnnDataExport.js:25-64) and the input scaling of `build_node_features` (train_baseline.py:26-39), rounded to Q24 where `build_node_features` rounds to float32 | `NodeFeatures`, `extract_node_features`, `model_input_q24`, `FRAC_BITS` |
| `jsnum` | JavaScript number arithmetic: binary64 `+ * /`, `Math.round`, `toFixed` | `Dbl` |
| `weights` | `vendor/gnn-sidecar/baseline_model.pt` as Q24 integers (generated by `tools/quantize.py`) | `CONV1_W` ... `EDGE2_B` |
| `model` | `EdgeLevelGNN.forward` as `inference_server.py` runs it, with torch_geometric 2.8.1 `GCNConv` | `edge_scores`, `score_pair`, `q24_to_e4`, `ModelError` |
| crate root | the L0 request of asolaria-score.mjs:121 (nodes `[actor, target]`, edge `[[0, 1]]`) | `observe_pair` |

`observe_pair(events, actor, target)` extracts the node features of every id in `events`, scores
the edge `actor -> target` and returns the sigmoid output in Q24 (units of 2^-24). It returns
`None` when either id never appears in the events, as asolaria-score has no L0 signal when :4792
does not answer. `gate/observed` turns that reading into gate inputs, and `asolaria observe`
(in `cli/`) runs it from the shell.

## Event format (HBP text)

One event per line, lines ending in LF; `#` comment lines and empty lines are ignored:

```
EVENT|actor=<id>|actor_type=<type>|target=<id>|target_type=<type>|risk=<integer>|status=<status>
```

- Every key is optional; an absent key is JavaScript `undefined`. An empty value of `actor`,
  `actor_type`, `target`, `target_type` or `status` is falsy, like an absent one, so an empty or
  absent id resolves to `"unknown"`, as `event.actor?.id || "unknown"` does.
- `risk` is `Number(event.risk?.score || 0)`: after percent-decoding, ASCII decimal digits, at
  most 1,000,000 (`risk=%31` is 1); absent is 0; `risk=` with no digits is refused. Event risk
  scores upstream (`scoreEdgeRisk`) are non-negative integers.
- Values are percent-escaped: `%25` for `%`, `%7C` for `|`, and every byte below 0x20 and 0x7F as
  `%XX` with uppercase hex. A field splits at its first `=`, so a later `=` belongs to the value
  (`target=a=b` is the id `a=b`, as is `target=a%3Db`). The decoded value must be UTF-8. A CR is
  a control byte, so a file with CRLF line endings is refused.
- Refused, with the line number: a row not starting with `EVENT`, a field without `=`, an unknown
  or duplicate key, a raw control byte, a lowercase or short escape, invalid UTF-8 after decoding,
  a non-decimal or over-limit risk, and more than 1,000,000 events.

`extract_node_features` keeps every detail of the JavaScript: the Map's insertion order; each
event visits `[actorId, targetId]`, the same id twice when actor equals target; a node's type is
set at first sight from the actor when `event.actor?.id === id`, else from the target; failures
count status `failed` or `error`; `avgRisk` and `failureRate` are `Math.round` of the binary64
quotient. Over the full input grid this differs from exact rational rounding in 574 of 1,684,600
`avgRisk` cases (for example 23/40 gives 57, where exact rounding gives 58) and in 2 of 80,600
`failureRate` cases; the port gives the JavaScript result in all of them.

## The forward

`src/model.rs` runs the forward of the running server, `inference_server.py`: two torch_geometric
`GCNConv` layers (self loops added where missing, duplicate edges counted, degree at the target,
symmetric normalisation, bias after propagation) with ReLU between them, then the edge head
`Linear(128, 64)`, ReLU, `Linear(64, 1)`, `Sigmoid` over the concatenated source and target
embeddings. Arithmetic is Q24 with i128 accumulation, one round-half-up per layer output, and a
fixed-point sigmoid that returns `floor(2^24 sigmoid(t) + 1/2)` exactly for every Q48 logit: a
range-reduced integer series, and, when its quotient lies within 2^-32 of a half, an exact decision
of the side from lower and upper sums of the series of `e^|t|` (code copied from
`model/l1-prototype`; see `PROVENANCE.md`). It equals the exact value from
`tools/sigmoid_referee.py` (integers) on 2,247 logits, 736 of them within 2^-32 of a half. Against
the vendored server `MODEL` under torch 2.14.1+cpu and torch_geometric 2.8.1, over the 3,273 scores
of the fixture pairs and random graphs the largest difference is 6 Q24 units (6 / 2^24), and over
the REQUEST rows it is 15 (case `search`, a two-node request found by a local search); the tests
allow 32 (32 / 2^24 = 2^-19).

`q24_to_e4` gives `+score.toFixed(4)` of the Q24 score in units of 1/10000, as
asolaria-score.mjs:122 rounds the L0 signal. For all 174 fixture request pairs it equals
`+score.toFixed(4)` of torch's float32 output. Over 100,000 fixed-seed request pairs with
features events can give (`tools/model_parity.py`), it differs by one e4 unit from torch's in 34
pairs when torch is fed the Q24 inputs and in 38 when torch is fed the float32 inputs of
`train_baseline.build_node_features`; torch's two inputs give different e4 values in 10. In each
of these the two scores lie on either side of a rounding midpoint `(k + 1/2) / 10^4`, within 16
Q24 units of it; the parity tool writes every pair whose torch score is within 32 units of a
midpoint as a REQUEST row, and `tests/model.rs` counts them. Two things contribute: the forward's
difference from torch, and the rounding of the score to Q24 before the fourth decimal (the
float32 grid is finer than Q24 below 1/2: 20,454 float32 values in [2^-15, 1) have a different
fourth decimal from their Q24 rounding, all below 1/2, and below 2^-15 both give 0;
`tests/model.rs` counts them in integers).

Where the L0 e4 value differs, the composite can differ by one e4 unit. Example (the REQUEST
case `e4_midpoint`): actor features (edge volume 88, avgRisk 803/100, maxRisk 9, failureRate
989/1000, trust tier 3) and target (53, 383/100, 4, 943/1000, 3). Rust gives 16,773,022 Q24 (e4
9998); torch gives the float32 with bits `3f7fef9d`, 16,773,021 / 2^24 (e4 9997). With payload
`heartbeat` and pid `BH.VERDICT.FLIP0000000001882` (Shannon 6129, baseline 410) the composite is
7200 and promoted here, and 7199 and not promoted with torch's value (gate/observed
`tests/e2e.rs`).

Every data file is HBP text (`KEY|k=v|k=v` rows, `#` comments). No JSON is read or written.

## Checks

From `model/l0-edge/`, as CI's `l0-edge` and `l0-torch-parity` jobs run them:

```sh
sha256sum -c UPSTREAM.sha256                       # vendored bytes unchanged
cargo +1.81.0 clippy --locked --all-targets -- -D warnings
cargo +1.81.0 test --locked
python3 -I tools/make_fixture.py --check           # stdlib referees: regenerate in memory, diff
python3 -I tools/quantize.py --check
python3 -I tools/features_referee.py --check
python3 -I tools/jsnum_referee.py --check
python3 -I tools/jsnum_referee.py --grid | cargo +1.81.0 run --locked -q --release --example jsnum_grid
python3 -I tools/sigmoid_referee.py --check        # CONST and SIGMOID rows of expected-model.hbp, no torch
<python with torch 2.14.1+cpu and torch_geometric 2.8.1> -I tools/model_parity.py --check
```

`tools/sigmoid_referee.py --check` is not yet in CI's `l0-edge` job or `scripts/check-all.sh`; the
integrator adds it after `jsnum_referee.py --grid`.

The torch check needs Python 3.13 with `torch==2.14.1+cpu` from
`https://download.pytorch.org/whl/cpu` and `torch_geometric==2.8.1` from PyPI (the versions named in
the header of `expected-model.hbp`). It compares float32 bit patterns byte for byte, and computes
its own comparisons in integers from those bit patterns.
`tools/model_parity.py` sets `ATEN_CPU_CAPABILITY=default`, `MKL_CBWR=COMPATIBLE`,
`OMP_NUM_THREADS=1` and `MKL_NUM_THREADS=1` before torch loads, so torch runs ATen's scalar
kernels and oneMKL's single SSE2 code path on every x86-64 CPU; see `PROVENANCE.md`.
`scripts/check-all.sh` runs it when `ASOLARIA_TORCH_PYTHON` names such a Python, and prints a SKIP
line otherwise.
